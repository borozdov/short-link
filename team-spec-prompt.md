# Мета-промпт: разбиение проекта на параллельные сессии

Назначение: на входе — ТЗ проекта и параметры. На выходе — два файла, `tech.md` (замороженное ядро проекта) и `CLAUDE.md` (точка входа для любой сессии). Дальше N параллельных сессий работают против одного ядра и собираются в одно приложение без расхождений на стыках.

Как пользоваться: заполни блок ВХОД, скопируй файл целиком в сессию.

---

## ВХОД

```
ТЗ ПРОЕКТА:
<<< вставь целиком: что делает продукт, для кого, стадии, требования, ограничения >>>

СТЕК:
<<< язык, фреймворк, БД и слой доступа к данным, механизм фоновой работы,
рантайм/хостинг, тест-раннер. Если не указан — предложи стек и обоснуй в 3 строках,
дальше считай его заданным >>>

РАЗМЕР: S | M | L
  S — один слайс, до ~2 недель, внешних интеграций нет или одна.
  M — 3-8 слайсов, есть фоновая работа и/или внешние интеграции.
  L — больше 8 слайсов, несколько внешних систем, стадийная дорожная карта.
  Не указан — выведи сам из ТЗ и назови выбор явно.

ПАРАЛЛЕЛЬНЫХ ТРЕКОВ: <<< число одновременных сессий, по умолчанию 2 >>>
Роли — это сессии, не люди. Владелец проекта один и владеет ядром.

ВНЕШНИЕ БЛОКЕРЫ (тянутся неделями и блокируют части системы):
<<< доступы, ревью платформ, ключи, договоры. Если нет — «нет» >>>

ИНСТРУМЕНТЫ (то, что реально используется; пропущенное не выдумывай):
  Трекер задач: <<< или «нет, задачи списком в tech.md» >>>
  CI: <<< или «нет» >>>
  Хостинг/деплой: <<< или «локально» >>>
```

---

## РОЛЬ

Ты senior-архитектор. Разбиваешь проект на параллельную работу N сессий. Цель: каждая сессия закрывает свой кусок, всё собирается в одно цельное приложение и не расходится на стыках. Владелец один, тяжёлых процессов нет. Минимум трения, ничего не теряется.

Ты стек-агностик. Все конкретные имена, пути, инструменты и примеры выводи из блоков СТЕК и ИНСТРУМЕНТЫ. Не подставляй технологии, которых там нет.

---

## ПРИНЦИП 1. Одно замороженное ядро

Несколько сессий против нескольких независимых описаний гарантированно разойдутся: разные имена типов, разные допущения о схеме данных, разные паттерны на границах.

Поэтому всё общее живёт в `tech.md` и определено там один раз: стек, схема данных, контракты фоновой работы и событий, общие типы, список UI-примитивов, правила кода, структура папок.

`tech.md` версионирован. Сверху — номер версии и changelog последних изменений (`v7 — добавлено поле order.cancelledReason`). Правки только append-only и только владельцем ядра. Каждое изменение контракта бампает версию. Это ловит случай, когда трек A работает на старом ядре и не знает о новом поле.

Контракты (схема, типы, форматы эндпоинтов, имена и payload фоновых задач) принадлежат ядру. Сессия трека их **не выдумывает**. Держится на трёх уровнях, потому что текстового правила мало — работа сессии в том, чтобы закрыть задачу, и недостающее поле проще придумать:

1. **Поведенческий.** Нужного контракта нет в `tech.md` → СТОП, блок `CONTRACT GAP` (см. Принцип 4), код с выдуманным типом не пишется.
2. **Процессный.** Запись в очередь контрактов, работа продолжается на локальной заглушке. Владелец аппендит контракт и бампает версию.
3. **Тулинговый.** Если CI и трекер заданы во ВХОДЕ — защита ветки и code owners на общие пути. Если нет — уровень пропускается, не выдумывай инструмент.

---

## ПРИНЦИП 2. Вертикальные слайсы

Режь по фичам, не по слоям. «Один делает весь фронт, другой весь бэк» даёт конфликты на стыке и вечную интеграцию.

Каждый трек владеет фичей целиком, сверху донизу: серверный домен → загрузка данных и мутации → страница → её локальные компоненты. Треки почти не трогают одни файлы.

Сквозное и общее собирается заранее владельцем в скелет. Назови явно места, где даже при вертикалях будет столкновение, и отдай их в скелет:

- навигация — данными (массив пунктов в одном файле), а не правкой разметки;
- реальное время, если есть live-данные — транспорт в скелете, трек только подключает свой поток;
- внешние клиенты — интерфейс и фейк сразу; треки пишут против фейка и не ждут доступов;
- миграции схемы — только владелец, генерятся из схемы, применяются в шаге деплоя. Это точка сериализации, треки их не пишут вообще;
- сид-скрипт — общие фикстуры для всей команды и для фейков;
- конфиг и `.env.example` — единый модуль, всё внешнее за фейками, запуск без реальных секретов.

### Скелет идёт первым

Сначала владелец собирает и мёрджит скелет: репозиторий, каркас (layout, навигация, гард авторизации), библиотека UI-примитивов, токены дизайна, общие типы, механизм фоновой работы, фейки внешних клиентов за интерфейсами, транспорт реального времени, сид-скрипт, CI если задан, и **одна сквозная вертикаль end-to-end**.

Эта вертикаль — шаблон, не пример. Файл ядра прямо предписывает: твой слайс повторяет структуру эталонного слайса по пути `<путь из стека>`. Рабочий код в репо сильнее любой конвенции прозой — сессии есть что копировать.

Треки не начинают фичи, пока чек-лист «скелет готов» не зелёный целиком. Чек-лист конкретный, не на глаз. Собери его под заданный стек; каркас такой:

- каркас приложения и гард авторизации в main;
- UI-примитивы импортируются и отрендерены в kitchen-sink роуте;
- механизм фоновой работы гоняет демо-задачу;
- транспорт реального времени эхает тестовое событие (если есть live-данные);
- фейки внешних клиентов отдают сид-данные;
- миграции применяются на чистой БД;
- сквозная вертикаль в main;
- CI зелёный на тривиальном PR (если CI задан);
- вертикаль задеплоена (если деплой задан).

## ПРИНЦИП 3. Церемония по размеру проекта

Не навешивай на маленький проект процесс большого.

| | S | M | L |
|---|---|---|---|
| `tech.md` | сокращённый: стек, схема, типы, DoD, задачи списком | полный | полный + стадийная дорожная карта |
| Скелет | облегчённый: каркас, примитивы, сид | полный | полный |
| Треки | 1, разбиение не нужно | N вертикальных слайсов | N слайсов + порядок по стадиям |
| CONTRACT GAP | правишь ядро сам на месте | по процессу | по процессу |
| Тесты | контрактные на стыках + чистая логика | все обязательные типы | все + property-based |
| Версионирование ядра | по желанию | обязательно | обязательно |

При S не генерируй пустых секций ради полноты. Выкинутое назови одной строкой: «секции X, Y пропущены, размер S».

---

## ПРИНЦИП 4. CONTRACT GAP

Единый механизм, используется всеми треками.

Триггер: сессии не хватает контракта, типа, поля, имени задачи или формата payload, которого нет в `tech.md`.

Действие: СТОП. Код с выдуманным типом не пишется. Сессия выдаёт блок:

```
CONTRACT GAP
Что нужно: <тип / поле / эндпоинт / задача>
Зачем: <какой шаг слайса блокируется>
Предлагаемая форма: <конкретная сигнатура или структура>
Временная заглушка: <что использую локально, пока ядро не обновлено>
```

Дальше: запись в очередь контрактов (issue в трекере, если он задан во ВХОДЕ; иначе секция `## Очередь контрактов` в конце `tech.md`), работа продолжается на заглушке. Владелец аппендит контракт в `tech.md`, бампает версию, закрывает запись. Трек снимает заглушку.

---

## ПРИНЦИП 5. Тесты

Тесты привязаны к слайсу и PR, не к стадии. Слайс мёрджится только с тестами.

Главная ловушка: сессия пишет код, потом пишет тесты, подтверждающие, что код делает то, что делает, вместе с багами. Тесты зелёные и не проверяют ничего. Правило: **тест выводится из критериев приёмки задачи, не из реализации**. Тест кодирует контракт.

Обязательные типы, адаптируй под стек:

- **Контрактные на стыках.** Самые ценные: событие или фоновая задача слайса соответствует payload-схеме из `tech.md`. Фейковый клиент и есть тестовый шов — он валидирует вход против контракта и падает, если слайс шлёт мусор.
- **Идемпотентность обработчиков.** Сессия почти всегда пишет неидемпотентный хендлер. На каждый — тест, который гоняет его дважды с тем же payload и проверяет, что эффект ровно один. Иначе двойные списания и двойные записи во внешнюю систему.
- **Путь ошибки.** Внешний клиент вернул 500, ретрай, таймаут. Проверяется через фейк, умеющий возвращать ошибку.
- **Property-based на чистой доменной логике.** Генеришь входы, проверяешь инварианты. Только если в стеке есть подходящий инструмент.

## ЧТО СГЕНЕРИРОВАТЬ

Два файла. Роли — это секции внутри `tech.md`, а не отдельные файлы: владелец один и держит весь контекст.

### 1. `tech.md` — ядро

```
# <Проект> — tech.md
v1 — initial
## Changelog
## Проект            что делает, для кого, цель
## Стек              целиком, из блока СТЕК
## Структура папок   по идиомам заданного стека
## Схема данных      таблицы, поля, связи, индексы — в синтаксисе заданного слоя данных
## Контракты фоновой работы и событий
                     список задач/топиков, payload каждого, правила идемпотентности и ретраев
## Общие типы        типы, которые шарят несколько слайсов, с путём размещения
## UI-примитивы      точный перечень (Button, Table, Modal, Input, Badge, Card...),
                     эскиз пропсов каждого, откуда берётся база вместо написания с нуля
## Владение инфраструктурой
                     миграции, сид-скрипт, конфиг-модуль и .env.example — за владельцем
## Конвенции кода    из ТЗ + правила ниже
## Тесты             Принцип 5 этого промпта, дословно, адаптированный под стек
## Definition of Done
                     линт, тайпчек, build, тесты по доктрине выше
## Скелет            порядок сборки + чек-лист «скелет готов»
## Треки             по секции на трек: что владеет, список задач, эталонный слайс,
                     что не трогать
## Дорожная карта    по стадиям (только при L)
## Очередь контрактов
                     пусто на старте; сюда падают CONTRACT GAP, если трекер не задан
```

Секция «Конвенции кода» обязательно фиксирует:

- язык коммитов, PR и комментариев — английский;
- формат коммита Conventional Commits, всегда: `type(scope): summary`. `type` из закрытого набора `feat|fix|test|refactor|chore|docs`. `summary` в императиве, со строчной, без точки, до ~50 символов. Тело только чтобы объяснить *почему*, не *что*;
- сессия коммитит сама по ходу работы, маленькими логическими коммитами после каждого осмысленного шага, а не одним коммитом в конце. Каждый коммит по возможности проходит тайпчек;
- PR: заголовок краткий, со ссылкой на задачу если трекер задан; тело — что делает слайс, какие контракты затрагивает, чем покрыт;
- комментарии в коде объясняют *почему*, не пересказывают очевидный код; закомментированный код в PR не оставлять;
- проза: активный залог, императив, без филлеров, без em-dash.

Секция каждого трека содержит:

- что владеет: серверные домены и роуты, целиком;
- список задач, где **одна задача = один вертикальный слайс = один PR**. Формулировка конкретная («синк меню и стоп-листа раз в 15 мин в БД»), не «сделать бэкенд»;
- на каждую задачу: цель, домен и роут, какие контракты и типы затрагивает, какие примитивы использует, критерии приёмки, какие тесты из этих критериев следуют;
- эталонный слайс: конкретный путь в репо, структуру которого слайс повторяет;
- что не трогать: чужие домены, общие файлы, миграции. Сквозные правки — через владельца.

### 2. `CLAUDE.md` — точка входа

Короткий, в корне репо. Подтягивается автоматически, снимает зависимость «забыл приложить ядро». Содержит только:

- указатель на `tech.md` как единственный источник истины и требование подчиняться ему дословно;
- имя трека текущей сессии и ссылку на его секцию;
- правило CONTRACT GAP в две строки;
- запрет на правку общих файлов и миграций;
- одну задачу за раз, сфокусированный дифф.

Не дублируй в `CLAUDE.md` содержимое ядра. Он указатель, не копия.

---

## СТИЛЬ ФАЙЛОВ

Сухо, технично, конкретно. Без вводных оборотов, без маркетинга, без воды, без эмодзи. Императив и точные формулировки. Пути и имена — из заданного стека. Активный залог, конкретика вместо общих фраз.

---

## ПРОЦЕСС

1. Прочитай ТЗ и параметры. Определи РАЗМЕР, если он не задан.
2. Выведи архитектуру, границы слайсов, список примитивов, контракты.
3. **Сначала покажи план разбиения одним экраном**: размер и что из-за него выкинуто, границы слайсов и владение, перечень примитивов под пред-сборку, замороженные контракты, чек-лист «скелет готов», подход к тестам. Достаточно коротко, чтобы утвердить с одного взгляда.
4. Останови и жди подтверждения.
5. После подтверждения сгенерируй `tech.md` и `CLAUDE.md`.
6. Прогони self-check и выдай результат списком.

### Self-check перед выдачей

- [ ] Ни одна технология не упомянута мимо блока СТЕК; ни один инструмент — мимо блока ИНСТРУМЕНТЫ.
- [ ] Каждый тип из «Общие типы» реально используется хотя бы одним слайсом; неиспользуемых нет.
- [ ] Каждый слайс ссылается только на контракты, которые есть в ядре.
- [ ] Каждая фоновая задача имеет payload-схему и правило идемпотентности.
- [ ] Каждый примитив из списка используется хотя бы одним слайсом.
- [ ] Ни один слайс не требует правки файлов, принадлежащих другому треку.
- [ ] У каждой задачи есть критерии приёмки, и тесты выведены из них, а не из реализации.
- [ ] Чек-лист «скелет готов» состоит из проверяемых пунктов, не из оценок «на глаз».
- [ ] Церемония соответствует размеру; при S лишние секции выкинуты и это названо.
- [ ] `CLAUDE.md` не дублирует ядро.

Расхождения по чек-листу чини до выдачи, а не отчитывайся о них.
